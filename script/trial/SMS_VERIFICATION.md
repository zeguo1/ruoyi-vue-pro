# 官网安全卡片的手机号验证

MGS 负责短信渠道调用、验证码状态、限流、错误次数、验证凭据及申请关联。知办负责原对话安全卡片、可信会话和用户确认。首期支持中国大陆 11 位手机号；手机号只作为验证后的联系方式，不用于合并两个不同的申请主体。

## 用户流程

1. 用户在知办客服中点击安全验证卡片，在卡片内填写手机号、获取并输入验证码。卡片字段不转成聊天消息或模型工具参数。
2. 知办服务端以独立 `SMS_VERIFICATION` 能力调用 MGS 的发送及校验接口，绑定同一稳定的服务 issuer + 会话 subject。此时不要求已有业务账号，但知办必须验证卡片所属会话，不能替模型指定的 subject 签名。
3. MGS 验证成功后，返回仅供知办服务端保存的短期 `verificationToken`。验证码不再用于其他验证动作；同一动作的网络重试可在凭据有效期内取得同一结果。
4. 知办将验证凭据附在可信开户工具请求头中，MGS 从自己的记录取得手机号，原子保存申请与已验证联系方式，随后关联运营 CRM 线索。该步骤不确认开户，也不创建账号。
5. 用户另外确认“开通体验”后，知办附加当前申请的确认依据调用 create-accounts。账号、权限、演示数据仍由后台原有编排逐步准备；公众号绑定及业务办理流程保持不变。

短信验证、用户确认、账号就绪、公众号绑定和首次业务完成是五个不同事实。不能因收到验证码、校验成功或某个接口 `code=0` 就宣称全部完成。

## 私有接口

接口采用 `mgs-trial-v2` HTTPS HMAC 签名，签名格式见 [KNOWDO_CONTRACT_DRAFT.md](KNOWDO_CONTRACT_DRAFT.md)。两者均要求独立 `SMS_VERIFICATION` 能力、稳定 Subject、`Verified: false`、独立动作 Idempotency 和新的 Nonce。Email、Confirmation、Verification 在本组请求中保持空值。不得通过浏览器直连，也不加入 Agent OpenAPI。

### POST /admin-api/crm/trial-verification/send

JSON body（仅虚构测试样例，不表示已向该号码发送）：

```json
{"mobile":"13800000001"}
```

成功处理响应结构：

```json
{"code":0,"msg":"","data":{"challengeId":"<MGS 实际返回的 UUID>","state":"SENT","expiresAt":"<实际 UTC ISO8601 时间>","resendAfterSeconds":60}}
```

尖括号是说明占位，不能当作可提交的业务值。`SENT` 只表示短信客户端返回受理成功，不保证用户已收到。`SENDING` 表示首次调用正在发送或其进程结果未落库，`UNKNOWN` 表示发送结果不确定，`SUPERSEDED` 表示已被新的获取动作替换，`VERIFIED` 表示原验证码已用于校验。同一发送幂等键始终返回原挑战状态，不重复发送；不得把 UNKNOWN 当成成功送达或立即自动重发。用户等待冷却后重新点击获取，使用新的动作幂等键。

限流在数据库 guard 锁下原子检查：同一主体或手机号的冷却间隔，按手机号、主体和全局分别计算的滚动 24 小时数量。失败/不确定的发送也计入限额，防止利用重试放大发送。任何发送网络调用均在数据库事务之外。

### POST /admin-api/crm/trial-verification/verify

```json
{"challengeId":"<发送接口实际返回的 UUID>","code":"<用户在安全卡片输入的六位验证码>"}
```

成功返回：

```json
{"code":0,"msg":"","data":{"verificationToken":"<64 位不透明凭据>","expiresAt":"<实际 UTC ISO8601 时间>"}}
```

验证码只对原 issuer + subject、当前挑战、有效期及有限尝试次数有效。错误次数在返回业务错误之前提交，不能被事务回滚清零；并发校验使用行锁。同一成功校验动作的精确重试可恢复同一凭据，另一个校验动作不能重复兑换；错误重试同样受次数上限限制。重新获取短信会使该主体旧的、尚未绑定申请的挑战及验证凭据失效。

返回的 verificationToken 不进入模型、聊天记录、提示词、CRM 备注、普通日志或连接器共享凭据。知办服务端将它关联原安全会话，并通过 `X-Mgs-Trial-Verification` 注入 submit 请求。新申请不接受 `X-Mgs-Trial-Email` 或模型自报手机号替代该凭据。

submit 校验凭据归属、有效期和绑定状态，原子创建/复用申请并保存 MGS 已验证的手机号。失败时申请/步骤/联系方式一起回滚，凭据不会因中途失败而丢失；成功重试仍返回同一申请。不能用同一申请的新验证结果覆盖已有不同手机号。到期凭据不能提交申请；用户需重新通过安全卡片验证，或在已知申请 ID 时查询本人状态。

## 凭据及日志

MGS 使用 SecureRandom 生成六位码，只保存独立秘密密钥计算的验证码 HMAC；验证凭据只保存摘要，不以明文落库。原有 `verified_email` 留作历史申请兼容，新手机号申请写入空邮箱及专用的已验证联系表；CRM 使用从该表取得的 mobile。

发送复用 MGS 现有短信模板、渠道和 SDK 客户端。通用 SmsSendService 会记录含验证码的模板参数和内容，因此本路径不经过通用短信日志/MQ 流程，只记录挑战状态，不存储明文短信正文。只接受已启用的真实短信渠道和仅含 `code` 参数的专用模板，禁用钉钉调试渠道；服务商失败响应或异常内容不返回、不记入普通日志。现有客户端初始化/刷新日志使用的渠道配置对象也已隐藏 apiKey、apiSecret 和回调 URL，实际日志调用路径有回归验证。服务商日志/SDK 调试及部署代理的请求记录也需由部署方关闭敏感正文记录。

两个私有接口隐藏于 Agent 文档、关闭访问日志并返回 no-store；校验失败采用专用异常处理，避免通用校验日志打印 rejectedValue。DTO 和私有结果的 toString 均脱敏。MGS 已持久化的手机号按业务数据权限和保留策略管理；本变更不清空历史记录。

## 配置与错误

新增 `mgs.trial.sms-verification`，默认关闭。必须配置已审批的实际短信模板和独立秘密密钥，不能使用服务签名或登录交付密钥。默认验证码 300 秒、凭据 600 秒、冷却 60 秒、最多错误 5 次、每手机号/主体滚动 24 小时各 5 次、全局 500 次；这些是关闭状态下的可调整保护默认值，需在启用前确认实际业务额度。不得让模型设置这些值。

秘密密钥轮换会使未完成的验证码及成功结果重取失效，用户需重新验证；已签发且仍有效的凭据可按其数据库摘要完成原绑定。不得把轮换变成自动创建新申请或覆盖已有联系方式。

| code（整数） | 含义 |
| --- | --- |
| 1020100001 / 1020100002 | 服务签名/能力无效，或 Nonce 重放 |
| 1020100003 | 新开户或短信配置未就绪 |
| 1020100005 | 幂等键、申请内容或已绑定手机号冲突 |
| 1020100015 | 短信冷却或发送限额 |
| 1020100016 | 参数/验证码/验证凭据无效、过期或尝试次数耗尽 |

发送渠道失败在挑战中保留 UNKNOWN；不向外暴露服务商错误内容。验证失败示例：

```json
{"code":1020100016,"msg":"短信验证无效、已过期或已达尝试上限，请重新验证","data":null}
```

短信通过不生成确认凭据。create-accounts 仍必须使用知办从当前申请确认动作获得的 `X-Mgs-Trial-Confirmation`。
